# `imageIdIndex` is the requested slice; invalidate on `PRE_STACK_NEW_IMAGE`

A Stack viewport's `getCurrentImageIdIndex()` changes synchronously when a slice is requested, but the image arrives asynchronously and CS3D fires `STACK_NEW_IMAGE` only when the load succeeds; a failed load reports nothing on the element (the error goes to the global `eventTarget`, and the returned promise still resolves). Rebuilding the Snapshot only on `STACK_NEW_IMAGE` therefore lagged the Engine by one slice during loads and stayed stale forever after a failure. We decided the Snapshot's `imageIdIndex` means the slice the Engine has been *told* to show — exactly what its getter reports — and we invalidate on `PRE_STACK_NEW_IMAGE`, which every load path fires on the element synchronously after the index is assigned; `STACK_NEW_IMAGE` stays subscribed because display can still change VOI. Rejected: a "rendered slice" meaning (the Engine exposes no getter for it, so the library would have to derive state of its own, against ADR 0001), the scroll target index (nobody asked), and a second `renderedImageIdIndex` field (out of v1 scope until a consumer needs it). Consequence: during fast scrolling the index runs ahead of the pixels on screen. This rests on CS3D firing `PRE_STACK_NEW_IMAGE` *after* assigning the index; the browser smoke test with a failing image loader is the guard for that assumption.


Addendum (2026-09-18): the field was renamed `sliceIndex` when Slice Position became common to every viewport kind (issue 10). The meaning above is unchanged: on a Stack it is `getSliceIndex()`, which is `getCurrentImageIdIndex()`.
