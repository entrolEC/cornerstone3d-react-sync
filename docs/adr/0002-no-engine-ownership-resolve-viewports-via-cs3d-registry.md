# No engine ownership — viewports resolve via the CS3D global registry

Hooks need a way to reach a viewport, and the obvious shapes are a React Provider holding a RenderingEngine or a library-owned engine singleton. We rejected both: apps already own engine policy (instance count, IDs — e.g. an app-level engine singleton), and `@cornerstonejs/core` already ships a global registry (`getEnabledElementByViewportId` / `getRenderingEngines`). So hooks take only a `viewportId` and resolve it through the CS3D registry; the library never creates, holds, or configures an Engine. Consequence: the library works unchanged with any engine-management strategy, and when a viewport doesn't exist (yet), hooks return `undefined` — absence is a normal state reported to the app, not an error the library handles.
